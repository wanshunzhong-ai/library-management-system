## 一、结论速览

系统的**架构与基础质量是好的**：三段式分层清晰、SQL 全参数化、密码 PBKDF2 加盐、公开字段白名单、错误码体系统一、日志不落敏感信息、前端全量 `esc()` 防 XSS、所有写操作都有防重复提交。

真正需要动手的集中在三处：

1. **借阅写路径的原子性不完整** —— 库存「扣减」方向做得对，但「还书回补」「借阅上限」「重复借」「续借次数」四个方向都存在 TOCTOU 竞态，且数据库没有兜底约束。这是唯一会**静默损坏数据**的一类。
2. **图书「下架」能力实际缺失** —— 删除时提示「可将总册数改为 0 下架」，但校验规则要求总册数 ≥ 1，**给出的方案执行不了**；概览页的「已下架书目」指标因此恒为 0。
3. **借还核心工作流不符合柜面习惯** —— 借书弹窗无法扫码直达、输入条码后不会自动选中、扫码枪的 Enter 无效，**存在借错书的现实风险**。

另外有两个「部署即高危」的默认值需要处理：默认会话密钥与默认管理员口令。

| 维度 | 最该改的一件事 |
| --- | --- |
| 逻辑 | 借阅写路径的校验移入事务 + 数据库加兜底约束 |
| 功能 | 图书下架（总册数允许为 0）+
 借书扫码直达 |
| 使用习惯 | 删除/还书确认显示书名而非内部 ID；批量还书 |

## 二、P0 · 数据正确性与安全（建议优先处理）

> 本节 P0-1 ~ P0-3 已于 2026-10-11 完成修复，保留原始问题描述供追溯。

### P0-1　还书并发会导致库存凭空增加 ✅已核实 ✅已修复

- **位置**：`library/loans/service.py:130-149`（关键在 `137-147`）；根因在 `library/db.py` 缺 `CHECK` 约束
- **问题**：`return_book` 先在事务外读一次 `returned_at` 判重，再在事务内执行两条 UPDATE。第二条回补库存
  `UPDATE books SET available_copies = available_copies + 1 WHERE id = ?` **既没有检查第一条 UPDATE 的 `rowcount`，也没有 `available_copies < total_copies` 的上界**。
- **影响**：两个并发还书请求（`app.py` 中 `threaded=True`）都通过了事务外判重 → A 正常归还，B 的
  `UPDATE loans ... AND returned_at IS NULL` 命中 0 行，但 **B 仍然给库存 +1** → `available_copies > total_copies`，
  账实不符且无法自愈。
  前端确认按钮有 `disabled` 保护（`app.js:892`），所以**单浏览器双击被挡住**；但多标签页 / 多终端 / 脚本调用仍可触发。
- **建议**：
  1. 事务内先 `UPDATE loans ... WHERE id=? AND returned_at IS NULL`，`rowcount == 0` 即抛 `ConflictError`，**只有命中才回补库存**；
  2. 回补加上界：`... WHERE id=? AND available_copies < total_copies`；
  3. 表级兜底 `CHECK (available_copies >= 0 AND available_copies <= total_copies)`（老库需重建表，或用启动自检替代）。
- **成本**：小（约 20 行）

### P0-2　借书的三项校验在事务之外，并发可突破上限与重复借 ✅已核实 ✅已修复

- **位置**：`library/loans/service.py:99-104`（校验）vs `:110`（事务开始）
- **问题**：`overdue_count`、`active_loan_count >= max_borrow`、`find_open_loan` 三个判定都用**事务外的独立 SELECT** 完成，
  事务内只做了库存扣减和 INSERT。两个并发请求共享同一份「事务前快照」，会双双通过校验。
- **影响**：同一读者并发借不同书 → 突破 `max_borrow`；并发借同一本书 → 产生**两条未归还记录**。
  `loans` 表上没有 `(book_id, member_id) WHERE returned_at IS NULL` 的唯一约束，数据库无法兜底。
- **建议**：
  1. 把成员状态 / 逾期 / 上限 / 重复借的判定全部移入 `with db.transaction()` 内；
  2. 增加部分唯一索引兜底：`CREATE UNIQUE INDEX idx_loans_open_unique ON loans(book_id, member_id) WHERE returned_at IS NULL;`（需先清理历史重复数据）；
  3. 借阅上限可用条件写入根治，或对 `members` 行加 `BEGIN IMMEDIATE` 串行化。
- **成本**：中

### P0-3　续借可突破次数上限 ✅已核实 ✅已修复

- **位置**：`library/loans/service.py:152-173`（`UPDATE` 在 `167-172`）
- **问题**：`renew_count >= max_renew` 的检查在事务外；事务内的 `UPDATE` 没有对 `renew_count` 做条件约束，也不检查 `rowcount`。
- **影响**：并发 / 多终端续借可让续借次数超过上限（上限 2 变成 3）。读者端按钮有禁用（`reader.js:269-270`）、管理端弹窗也禁用，因此同样是**跨终端**才触发。
- **建议**：条件写入 `... SET renew_count = renew_count + 1 WHERE id=? AND returned_at IS NULL AND renew_count < ?`，并检查 `rowcount`。
- **成本**：小

### P0-4　默认密钥与默认管理员口令可预测 ✅已核实 ✅已修复

- **位置**：`config.py:112`（`LIBRARY_SECRET_KEY` 默认 `dev-only-insecure-key`）、`config.py:118`（`LIBRARY_ADMIN_PASSWORD` 默认 `admin123`）
- **问题**：未设置环境变量时使用固定默认值；`.env.example` 也只是文字提示「please-change-me」。
- **影响**：会话签名密钥可预测 → 可伪造会话直接以管理员身份访问；默认管理员口令是公开常识。
- **建议**：`debug=False` 时若 `LIBRARY_SECRET_KEY` 仍为默认值，**在 `load_config()` 直接拒绝启动**（fail fast，与现有配置校验风格一致）；首次用默认口令登录时强制改密。
- **成本**：小
- **实际做法**：
  1. **会话密钥**（真正的漏洞：可伪造会话绕过口令）：移除固定默认值，未配置时**自动生成 48 字节随机密钥并落盘到数据目录 `.secret_key`**（0600，已加 `.gitignore`），重启沿用同一密钥、不会踢掉登录；显式配置示例值或 <16 字符时，生产模式**直接拒绝启动**（`ConfigError`），开发模式仅告警。既保住了「开箱即用」，又让每套部署的密钥互不相同、不可预测。
  2. **默认管理员口令**：**没有**改成强制改密（会破坏文档中的演示账号与开箱即用体验，且要动 Schema 与整条登录链路）。改为三处可见的提醒：启动日志告警、`/api/auth/me` 回带 `security.default_admin_password`、后台控制台顶部常驻红色横幅 + 一键改密（改完自动消失）。若要升级为「强制改密」，代价是给 admins 加 `must_change_password` 列 + 守卫拦截 + 前端阻塞弹窗，并且要同步改写 `smoke_test.py` 里所有以 `admin123` 登录的用例。

### P0-5　限流可被伪造 `X-Forwarded-For` 绕过 ✅已核实 ✅已修复

- **位置**：`library/auth/routes.py:18-22`（无条件取 XFF 第一跳）、`library/auth/service.py`（限流 key = `账号|IP`）
- **问题**：攻击者每次换一个伪造的 XFF 头就得到一个新的限流桶，**锁定机制形同虚设**，同时污染日志里的 IP。
- **建议**：仅在受信代理场景启用 XFF（新增 `LIBRARY_TRUSTED_PROXIES`），否则一律用 `request.remote_addr`；另外给「账号」维度单独计数（不绑定 IP）。
- **成本**：小
- **实际做法**：新增 `LIBRARY_TRUSTED_PROXIES`，`client_ip()` 只在**对端确属受信代理**时采信 XFF，且**从右向左取第一个非受信地址**（防止伪造链左侧注入）；未受信时一律 `remote_addr`。顺带合并了 `auth/routes.py` 与 `auth/service.py` 里两份重复的取 IP 实现。限流改为双桶：`账号|IP`（阈值 5）+ `IP`（阈值 ×5，兜住同源轮换账号名的喷洒），登录成功同时清空两个桶。

### P0-6　手机号可撞他人借书证号，造成登录身份混淆 ✅已核实 ✅已修复

- **位置**：`library/reader/service.py:290-296`（自助改号只查 `phone` 冲突）＋ `library/members/repository.py:66-73`（登录按 `card_no OR phone` 匹配、`ORDER BY id LIMIT 1`）
- **问题**：两条路径口径不一致：
  1. 读者自助改手机号时，**只检查是否与其它读者的 `phone` 重复，不检查是否撞上别人的 `card_no`**。于是读者 A 可把手机号设成读者 B 的证号；
  2. 登录 SQL 用 `card_no = :account OR phone = :account ORDER BY id LIMIT 1` 消歧义 → 命中 id 较小者，产生**身份抢占**（A 用 B 的证号登录时可能登进 B 的账户）。
  3. 管理员新增/编辑读者的路径**完全没有手机号唯一性校验**，同一手机号可被多个读者持有。
- **建议**：抽一个统一的「该值不得命中任何他人的 `card_no` 或 `phone`」校验函数，两条路径共用；给 `members(phone)` 加部分唯一索引 `WHERE phone <> ''`。
- **成本**：小
- **实际做法**：新增 `members/service.ensure_identifier_available()`，管理员建档 / 管理员改档 / 读者自助改手机号三条路径共用，同时校验「撞他人证号或手机号」与「撞后台管理员工号」（工号重名会让读者永远登不进来）。`members(phone) WHERE phone <> ''` 建部分唯一索引兜底（老库有重复时告警跳过，交 `check_consistency()` 报告，不擅自清空联系方式）；登录查询改为优先匹配证号。手机号冲突的错误码统一为 409（与证号重复一致），原先是 422。

### P0-7　（新发现）演示数据生成器会造出重复在借，且老库缺索引时无人知晓 ✅已核实 ✅已修复

- **位置**：`library/seed.py` 借阅计划生成段（原 `85-94`）；`library/db.py` `_create_open_loan_index`
- **问题**：第 1 批给 `loans(book_id, member_id) WHERE returned_at IS NULL` 加了唯一索引，但**演示数据生成器只用 `open_counter[book_id]` 卡了「同一本书的在借册数不超过总册数」，没有卡「同一读者不能同时借同一本书两次」**。用固定随机种子（`20261010`）跑 `--reset` 就会造出重复在借 → 唯一索引建不上 → 第 1 批的数据库兜底在真实库上**静默失效**。本次核对用户库时正好命中：`loans` 第 11、45 条同为《宇宙的琴弦》/陈雨欣且都未归还，`idx_loans_open_unique` 不存在。
- **影响**：批 1 承诺的「数据库层兜底」在受影响实例上并不存在（应用层校验仍在），且没有任何地方提示索引缺失。
- **实际做法**：
  1. 生成器增加 `open_pairs` 集合，同一读者同一本书只允许一条在借计划；
  2. 新增 `db.repair_consistency()`：把重复在借里**较晚的那些标记为已归还**（归还时间取其应还日期）并同步把库存补回，然后补建唯一索引 —— 只处理这一种有明确答案的问题，其余交人工；
  3. 新增 `python app.py check`（只读体检，退出码非 0 表示有问题）与 `python app.py repair`；
  4. `check_consistency()` 增加重复手机号、手机号抢占证号、读者标识遮蔽管理员工号三类体检项。

### P1-1　图书「下架」不可用，且提示文案指向做不到的操作 ✅已核实 ✅已修复（2026-10-11）

- **位置**：`library/books/service.py:145`（删书提示「可将总册数改为 0 下架」）vs `library/books/service.py:31`（`total_copies` 最小值限定为 **1**，`update_book` 同样走 `_normalize`）＋ `library/dashboard/repository.py:17`（统计 `total_copies = 0` 的 `off_shelf_titles`）
- **影响**：**有历史借阅记录的书既不能删、也不能下架**，只能永久挂在架上；概览页的「已下架书目」指标永远是 0，属于设计未闭环。
- **实际做法**：
  1. `total_copies` 允许为 0；新增专用端点 `POST /api/books/:id/shelf {total_copies}`（0 = 下架，正数 = 上架 / 调库），校验（含在借数）与写入同处一个 `BEGIN IMMEDIATE` 事务，保证 `可借数 = 总册数 - 在借数`；图书列表 / 详情补 `off_shelf` 字段；
  2. 门户整体隐藏下架书：检索 / 新书榜 / 分类 / 门户统计都排除 `total_copies = 0`；借书被拒时提示「已下架，无法借出」；
  3. 前端图书列表加「下架 / 上架」按钮与「已下架」徽标（整行降噪），详情弹窗同样提供入口；概览「馆藏书目」卡片显示「已下架 N 种」；编辑表单的提示文案同步说明「填 0 表示下架」；删书提示改为指向真实可行的下架操作。
- **验证**：新增 24 项断言（含「有在借时下架被拒 409」「下架后门户检索不到」「上架后可借数恢复」「概览已下架计数归零」「下架闭环后库存对账一致」），并经无头 Chrome 截图核对。

### P1-2　借书弹窗无法扫码直达，存在借错书风险 ✅已核实 ✅已修复（2026-10-11）

### P1-5　逾期当天显示「逾期 0 天 / 罚金 ¥0」 ✅已核实 ✅已修复（2026-10-11）

- **验证**：构造「应还 = 今天 00:00、当前时刻已过」的记录，断言状态为**在借**、天数为 0；断言逾期筛选内每条天数 ≥ 1、

- **成本**：小
